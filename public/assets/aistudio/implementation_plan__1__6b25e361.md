# بازطراحی معماری تمپلیت Astro v7 با جداسازی لایه هسته و مشتری (Zero-Conflict Upstream Architecture)

این طرح ساختار تمپلیت استارتر Astro v7 را به‌گونه‌ای بازطراحی می‌کند که وب‌سایت‌های ساخته‌شده با **Use this template** در گیت‌هاب، بدون تداخل (Conflict) هنگام merge با مخزن بالادستی (**upstream**) به‌روزرسانی شوند، در حالی که **تمام ویژگی‌های کاربردی و قواعد اصلی معماری تمپلیت به‌صورت کامل و دست‌نخورده حفظ می‌شوند**.

---

## User Review & Critical Decisions

> [!IMPORTANT]
> بر اساس بازخورد شما، در این نسخه از طرح، **جدول تضمین حفظ قواعد اصلی و امکانات کاربردی تمپلیت** اضافه شده است. هیچ قابلیتی از هسته حذف نمی‌شود؛ تنها نقطه تغییر، انتقال «تعریف‌ها، هویت مشتری، محتوای دمو و نقاط سفارشی‌سازی» از لایه هسته به لایه ایزوله مشتری است.

- **سطح بازطراحی**: بازطراحی کامل لایه جداسازی هسته (Core) و لایه مشتری (Client) به‌همراه همگام‌سازی کامل اسکریپت‌های CLI، ممیزی i18n، تست‌های واحد و تست دود خروجی.
- **مدیریت محتوای دمو**: انتقال صفحات، مقالات، پروژه‌ها و تصاویر دمو به یک **بسته نمونه مستقل (Starter Kit)** بیرون از مسیر محتوای فعال مشتری، همراه با امکان وارد کردن انتخابی دمو هنگام راه‌اندازی پروژه جدید.
- **پیکربندی زبان**: حفظ معماری دوزبانه **فارسی و انگلیسی** به‌عنوان حالت پیش‌فرض، با امکان انتخاب زبان پیش‌فرض پروژه و افزودن یا محدود کردن زبان‌ها از لایه مشتری بدون دستکاری موتور i18n هسته.
- **لایه سفارشی‌سازی (Override Layer)**: ایجاد لایه اختصاصی مشتری برای بازنویسی تنظیمات، توکن‌های تم و CSS، پیام‌های ترجمه، منوهای ناوبری، قالب‌های صفحه، آیکون‌های اضافی و قلاب‌های چیدمان اصلی.

## 1. Overview & Core Concept

- **اصل بنیادین — «جداسازی مالکیت بدون کاهش قابلیت»**:
  - **لایه هسته (Upstream-Owned Core)**: شامل تمام موتورهای فنی تمپلیت (روتینگ یکپارچه، سیستم محتوا و کالکشن‌ها، ۲۲ بلوک UI، موتور جستجوی فارسی Pagefind، سیستم تم OKLCH و سطوح شیشه‌ای، انیمیشن‌های ChronoTrig و Lenis، مدیریت کوکی GDPR، سئو و اسکیمای JSON-LD، تولید کارت‌های OG، و کل ابزارهای CLI) است. آپدیت‌های upstream فقط این لایه و بسته نمونه را لمس می‌کنند.
  - **لایه مشتری (Client-Owned Workspace)**: شامل تنظیمات اختصاصی برند، استایل‌ها و متغیرهای تم تکمیلی، دیکشنری پیام‌های اختصاصی مشتری، ساختار منوها و لینک‌های حقوقی، تعریف زبان‌های فعال پروژه، قالب‌ها و بخش‌های سفارشی، و کل محتوای واقعی سایت است.
- **تضمین حفظ قواعد غیرقابل مذاکره (Prime Directives)**:
  - **Pure SSG بدون سرور**: خروجی کاملاً ایستا، بدون سرور ران‌تایم، همراه با فرم‌های Pure-SSG متصل به API خارجی یا fallback ایمیل.
  - **الگوی روتر واحد (Lean Router Dispatcher)**: تمام صفحات و کالکشن‌ها همچنان از یک نقطه مرکزی دیسپچ می‌شوند و هیچ مسیر پویای پراکنده‌ای ایجاد نمی‌شود.
  - **زبان پیش‌فرض بدون پیشوند و تغییر زبان استاتیک**: مسیر زبان پیش‌فرض بدون پیشوند و سایر زبان‌ها با پیشوند ایستا و ناوبری کامل مرورگر برای حفظ `lang`، `dir` و تایپوگرافی دقیق.
  - **RTL-Native و ویژگی‌های منطقی CSS**: حفظ کامل قانون صفر خطا در ممیزی ویژگی‌های منطقی (`ms-`, `me-`, `ps-`, `pe-`, `start-*`, `end-*`, گرادیان‌های معکوس در RTL) و ایزولاسیون بلوک‌های کد.
  - **مصرف رندر-تایم پیام‌های Paraglide و سیستم آیکون بسته**: بدون ویرایش دستی فایل‌های کامپایل‌شده Paraglide و با حفظ بهینه‌سازی ایمپورت تک‌آیکون (بدون بارگذاری کل پکیج Tabler).

## 2. User Experience & Visual Design

این بازطراحی تجربه بصری و کیفیت مهندسی تمپلیت را برای بازدیدکننده نهایی عیناً حفظ کرده و تجربه توسعه‌دهنده (DX) را برای کار با چند پروژه مشتری بهینه می‌کند:

- **جریان کاری مهندس نرم‌افزار (Onboarding & Upstream Sync Flow)**:
  1. ایجاد ریپوزیتوری جدید از روی تمپلیت و اتصال مخزن اصلی به‌عنوان `upstream`.
  2. اجرای ویزارد راه‌اندازی مشتری برای تنظیم نام برند، رنگ و فونت OKLCH، زبان پیش‌فرض (`fa` یا `en`)، انتخاب دریافت یا عدم دریافت صفحات/مقالات دمو از Starter Kit، و تولید خودکار آیکون‌ها و OG Image برند.
  3. توسعه اختصاصی پروژه مشتری (ویرایش منوها، افزودن قالب‌های سفارشی یا بخش‌های جدید، نوشتن محتوای فارسی/انگلیسی) منحصراً درون مرز لایه مشتری.
  4. دریافت آپدیت‌های بعدی تمپلیت از `upstream` با حداقل یا صفر Conflict و بررسی خودکار سلامت پروژه با زنجیره کامل `doctor`، `audit:i18n`، `lint`، `test`، `build` و `smoke`.
- **تداوم هویت بصری و طراحی دوزبانه**:
  - *پالت OKLCH و Dark/Light Mode*: تمام نقش‌های رنگی معنایی، کنتراست WCAG AA، حالت تاریک/روشن بدون پرش (Fouc-free inline script) و سطوح شیشه‌ای Header حفظ می‌شوند.
  - *تایپوگرافی و تقویم بومی*: فونت‌های فارسی (`Vazirmatn` / `Noto Sans Arabic`) و لاتین، اصلاح `letter-spacing: 0` در RTL، اعداد بومی و تقویم هجری شمسی در زبان فارسی کاملاً حفظ می‌شوند.
  - *موتور حرکت و چاپ*: رفتار یکپارچه ChronoTrig، Lenis و کاهش حرکت (`data-motion="reduced"`) به‌همراه استایل چاپ تمیز (`@media print`) دست‌نخورده باقی می‌ماند.

## 3. Key Product Decisions & Trade-Offs

### جدول تضمین حفظ ویژگی‌های کاربردی (Feature Preservation Matrix)

| دسته قابلیت | وضعیت در معماری جدید | مکانیزم حفظ در ساختار دولایه |
| :--- | :--- | :--- |
| **۱۹ بخش آماده لندینگ و ۳ ابزارک UI** | حفظ ۱۰۰٪ بدون تغییر رفتاری | در لایه هسته باقی می‌مانند؛ هم با پیام‌های پیش‌فرض Paraglide و هم با props سفارشی در صفحات/قالب‌های مشتری کار می‌کنند. |
| **سیستم بلاگ، فیلتر کلاینتی و کالکشن پروژه‌ها** | حفظ ۱۰۰٪ + توسعه‌پذیر | صفحه‌بندی، TOC، زمان مطالعه، مقالات مرتبط، کپی کد، Atom Feed و فعال/غیرفعال‌سازی ماژول‌ها از طریق کانفیگ ادغام‌شده کار می‌کنند. |
| **جستجوی Pagefind + نرمال‌سازی فارسی** | حفظ ۱۰۰٪ | ایندکس‌ساز بیلد و جستجوی دوزبانه (پشتیبانی از نیم‌فاصله، ی/ک عربی-فارسی و ارقام) بدون تغییر در هسته حفظ می‌شوند. |
| **سئو، Open Graph برندشده، Sitemap و Manifest** | حفظ ۱۰۰٪ | خروجی‌ساز SVG→PNG کارت‌های OG، متاتگ‌های `hreflang`، اسکیمای JSON-LD و مانیفست PWA مستقیماً از کانفیگ ادغام‌شده مشتری می‌خوانند. |
| **مدیریت کوکی GDPR و فرم‌های Pure-SSG** | حفظ ۱۰۰٪ | بنر/مودال رضایت کوکی، Script Gatekeeper و فرم تماس/خبرنامه بدون سرور از تنظیمات مشتری تغذیه می‌شوند. |
| **زنجیره کامل اسکریپت‌های CLI و ممیزی** | حفظ ۱۰۰٪ + ارتقا | تمام دستورات ساخت صفحه/پست، مدیریت زبان، ممیزی i18n، بررسی لینک‌ها و تست دود با لایه مشتری و Starter Kit سازگار می‌شوند. |

### تصمیم‌های کلیدی جداسازی هسته و مشتری

1. **ادغام عمیق پیکربندی (Core Defaults + Client Config Override)**:
   - *رویکرد*: هسته مقادیر پایه و اسکیمای Zod را نگه می‌دارد؛ لایه مشتری فقط فیلدهای اختصاصی برند و ماژول‌ها را بازنویسی می‌کند و هر دو در بیلد و کلاینت (نسخه سبک بدون Zod) ادغام می‌شوند.
   - *چرا*: افزودن ویژگی یا کلید پیکربندی جدید در upstream بدون تداخل به پروژه‌های قدیمی منتقل می‌شود و اسکیما هیچ‌گاه نمی‌شکند.
2. **دیکشنری‌های دوزبانه دولایه (Core Messages + Client Messages)**:
   - *رویکرد*: پیام‌های سیستمی هسته و پیام‌های اختصاصی مشتری در فایل‌های مجزا نگهداری شده و در مرحله پیش‌کامپایل (پیش از Paraglide) به شکل خودکار ادغام می‌شوند؛ خروجی ادغام‌شده در `.gitignore` قرار می‌گیرد.
   - *چرا*: مشتری کلیدهای `nav_*`، دسته‌بندی‌های بلاگ و متون بازاریابی خود را تغییر می‌دهد یا پیام‌های هسته را override می‌کند، در حالی که آپدیت کلیدهای جدید هسته در upstream بدون conflict انجام می‌شود.
3. **بسته نمونه مستقل به‌جای دموهای چسبیده به محتوا (Starter Kit Isolation)**:
   - *رویکرد*: تمام صفحات و پست‌های دمو به‌همراه تصاویرشان به یک بسته نمونه منتقل می‌شوند. مسیر محتوای فعال پایه در تمپلیت تنها یک صفحه خانه خنثی و معتبر دارد و اسکریپت راه‌اندازی می‌تواند در شروع پروژه جدید (با فلگ یا پاسخ بله در ویزارد) دمو را به لایه مشتری کپی کند.
   - *چرا*: اگر مشتری دموها را حذف یا بازنویسی کند، آپدیت بعدی upstream روی بسته نمونه هیچ تداخل `modify/delete` با محتوای مشتری نخواهد داشت و هم‌زمان CI تمپلیت هم روی حالت پایه و هم حالت دمو قابل تست است.
4. **ناوبری و لینک‌های حقوقی کاملاً بیرون از هسته (Client Navigation Registry)**:
   - *رویکرد*: لیست صفحات منو، زیرمنوها، ستون‌های فوتر و لینک‌های حقوقی به لایه مشتری منتقل می‌شوند؛ هسته فقط موتور محاسبه مسیر منتشرشده، وضعیت Active و رندر منوها را انجام می‌دهد.
   - *چرا*: تغییر ساختار منوی مشتری دیگر نیازی به ویرایش فایل‌های منطق هسته ندارد.
5. **نقاط توسعه و بازنویسی لایه مشتری (Theme CSS، Page Templates، Layout Hooks و Icons)**:
   - *رویکرد*:
     - **Theme & CSS**: فایل استایل اختصاصی مشتری بلافاصله پس از استایل‌های هسته بارگذاری می‌شود تا بازنویسی متغیرهای `--theme-*` و افزودن کلاس‌های اختصاصی در آنجا انجام شود.
     - **Page Templates & Content Types**: رجیستری قالب‌های صفحه مشتری پیش از قالب‌های هسته بررسی می‌شود تا ساخت قالب اختصاصی `.astro` در لایه مشتری نیاز به ویرایش `PageView` یا قفل `enum` در اسکیمای هسته نداشته باشد.
     - **Layout Hooks**: قلاب‌های استاندارد برای بخش‌های تکرارشونده (مانند نشان/لوگوی هدر، بخش‌های تکمیلی فوتر، و متاتگ/اسکریپت اضافی در `<head>`) از لایه مشتری به لایه اصلی تزریق می‌شوند.
     - **Icons Registry**: امکان ثبت آیکون‌های اضافه مشتری در لایه مشتری و ادغام با واژگان بسته آیکون‌های هسته بدون دست زدن به لیست مرکزی هسته (با حفظ الگوی ایمپورت تک‌آیکون برای سرعت بیلد).
6. **تنظیمات زبان مشتری (Bilingual FA/EN Default + Client Locale Definition)**:
   - *رویکرد*: تعریف زبان‌های فعال پروژه، زبان پیش‌فرض (`fa` یا `en`) و متادیتای زبان‌های اضافه در لایه مشتری قرار می‌گیرد و موتور i18n هسته به‌همراه تنظیمات Paraglide و اسکریپت‌های ممیزی به صورت خودکار با آن همگام می‌شوند.
   - *چرا*: افزودن زبان سوم یا تغییر زبان پیش‌فرض در یک پروژه مشتری، فایل‌های موتور هسته را دچار conflict با upstream نمی‌کند.

> [!WARNING]
> پس از ایجاد مخزن جدید از دکمه **Use this template** در گیت‌هاب، تاریخچه کامیت‌های پروژه مشتری از مخزن تمپلیت جداست؛ بنابراین **فقط در اولین همگام‌سازی** با upstream لازم است پرچم `--allow-unrelated-histories` در گیت استفاده شود و پس از آن تمام مرج‌های بعدی به‌صورت استاندارد و بدون این پرچم انجام می‌شوند. این موضوع در راهنمای همگام‌سازی و اسکریپت کمکی پروژه مستند خواهد شد.

### Data Model & Merge Resolution Strategy

1. **مدل ادغام پیکربندی (Deterministic Deep Merge)**:
   - آبجکت پایه هسته به‌عنوان منبع مقادیر پیش‌فرض عمل می‌کند.
   - فایل پیکربندی مشتری فقط فیلدهای تغییریافته را نگه می‌دارد.
   - موتور ادغام، مقادیر تو در تو را کلید-به-کلید ترکیب کرده، آرایه‌ها را جایگزین می‌کند، و خروجی نهایی را از اعتبارسنجی Zod عبور می‌دهد. ماژول سبک کلاینت نیز بدون ایمپورت Zod همین ترکیب را برای اسکریپت‌های مرورگر فراهم می‌کند.
2. **خط لوله پیام‌های دوزبانه (Two-Tier Message Merge)**:
   - هسته دارای دیکشنری پیام‌های سیستمی (جستجو، کوکی، دسترس‌پذیری، ناوبری پایه، خطای ۴۰۴، برچسب‌های UI بلاگ و پیش‌فرض‌های ۲۲ بلوک) برای زبان‌های پایه است.
   - لایه مشتری دارای دیکشنری اختصاصی مشتری برای هر زبان فعال است که می‌تواند کلیدهای جدید اضافه کند یا هر کلید هسته را بازنویسی کند.
   - ابزار پیش‌کامپایل پیام‌ها دو لایه را برای هر زبان فعال ادغام کرده و در مسیر موقت `.gitignore`شده قرار می‌دهد تا Paraglide یک مجموعه کامل تایپ‌شده تولید کند. دستورات CLI افزودن صفحه یا کلید ترجمه، همیشه تغییرات را در لایه مشتری ذخیره می‌کنند.
3. **جریان تفکیک دمو و محتوای مشتری (Starter Kit Seeding)**:
   - مخزن تمپلیت یک صفحه خانه حداقلی و استاندارد در مسیر محتوای فعال دارد تا بیلد، روتینگ، سئو و تست دود تمپلیت همیشه به‌صورت مستقل سبز باشد.
   - بسته نمونه کامل (صفحات معرفی، امکانات، تعرفه، نمایش ۲۲ کامپوننت، مقالات و پروژه‌های دمو) در یک فضای مجزای Starter Kit قرار دارد.
   - هنگام اجرای ویزارد راه‌اندازی مشتری (یا دستور مستقل وارد کردن دمو)، توسعه‌دهنده انتخاب می‌کند که آیا دموها به لایه محتوای مشتری منتقل شوند یا پروژه با اسکلت تمیز شروع شود. همچنین برای پروژه‌هایی که بخش‌های خاص دمو را نمی‌خواهند، پاک‌سازی فقط در لایه مشتری انجام می‌شود و هیچ پیوندی با upstream ندارد.
4. **نقشه تعامل رجیستری و هوک‌های ظاهری (Registry & Hook Resolution)**:

```text
  Request / Component Render
         │
         ├──► Theme CSS ─────► Core CSS (OKLCH/Glass/Motion) + Client Override CSS
         │
         ├──► Navigation ────► Client Nav Definition ──► Core Route/Publish Resolver
         │
         ├──► Page Template ─► Client Template Map ──► Core Template Map ──► MDX Body
         │
         ├──► Layout Chrome ─► Core BaseLayout ◄── Client Slots (Head / Brand / Footer)
         │
         └──► Icons ─────────► Client Extra Icons ──► Core Tabler Icon Map
```

5. **استراتژی گیت و همگام‌سازی بدون تداخل (Upstream Sync Contract)**:
   - خروجی‌های موقت ترکیب‌شده (دیکشنری ادغام‌شده، خروجی کامپایل Paraglide، کش بیلد) در `.gitignore` ایزوله می‌شوند.
   - فایل‌های هویتی پروژه (مانند متادیتای اپلیکیشن) با قوانین `.gitattributes` و/یا دستورالعمل استاندارد مدیریت می‌شوند.
   - افزودن یک دستور کمکی همگام‌سازی/ممیزی (`upstream:check` یا بخش مشخص در `doctor`) به مهندس اجازه می‌دهد بلافاصله بعد از `git merge upstream/main` از سلامت ادغام، تساوی پیام‌ها و سازگاری کانفیگ مشتری با نسخه جدید هسته مطمئن شود.

### Verification & End-to-End Quality Gates

پس از پیاده‌سازی، سلامت و حفظ کامل تمام قابلیت‌ها از طریق موارد زیر راستی‌آزمایی می‌شود:
- **تست‌های واحد (`vitest`)**: تست تمام ماژول‌های فعلی به‌علاوه تست‌های جدید برای Deep Merge کانفیگ، ادغام دیکشنری‌های دولایه، رجیستری قالب‌ها/آیکون‌های مشتری و موتور ناوبری.
- **ممیزی جامع (`audit:i18n` و `doctor`)**: اطمینان از هم‌خوانی زبان‌ها (`fa`/`en`)، نبود کلید مرده، نبود تداخل مسیر و رعایت ۱۰۰٪ ویژگی‌های منطقی RTL.
- **بیلد، Smoke Test و بررسی لینک‌ها (`lint`، `build`، `smoke`، `link:check`، `knip`)**: اطمینان از تولید صحیح خروجی استاتیک، متاتگ‌های سئو، کارت‌های OG، جستجوی Pagefind فارسی/انگلیسی و صحت تمام ۲۲ بلوک UI.
- **تست چرخه کامل CLI (`verify:cli`)**: اجرای آزمایشی تمام دستورات ساخت صفحه، پست، تغییر زبان، راه‌اندازی مشتری و ایمپورت دمو در محیط ایزوله.
